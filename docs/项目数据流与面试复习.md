## 1. 普通终端问答的数据流

```text
cli.main → run_answer
  → build_retriever：读配置、加载文档、规范化、切块、构造检索器
  → retriever.search(question, top_k)
      BM25 + BGE → RRF候选 → Cross-Encoder → 最终Top-K
  → generator.generate(question, results)
      编号证据 → system/user提示词 → 模型请求
  → GenerationResult：回答、Token用量和耗时
  → 终端打印
```

原生Agent走 `agent.main → KnowledgeTools.from_config → run_agent`：模型先提出工具调用，本地校验并执行 `search_knowledge` 或 `read_document`，将结果按 `tool_call_id` 送回，再由模型继续调用或回答。搜索使用配置指定的检索链，补读按来源ID和规范化字符窗口读取。

普通问答生成答案后结束。Judge只在答案评测入口运行。

## 3. 必须能解释的关系

- `Document → Chunk → SearchResult`：全文变成可追踪片段，再携带排序分数；source保持原文身份，start/end指向规范化文本的字符区间。
- BM25匹配词项，BGE匹配向量语义。RRF融合名次，避免直接相加不同尺度的原始分数。
- Cross-Encoder联合处理问题与片段，因此用于小候选集；`candidate_k` 是候选规模，`top_k` 是最终返回规模。
- 固定RAG由程序安排检索步骤，Agent允许模型选择工具和查询。Schema只描述工具，程序负责校验和执行。
- 引用编号有效，只说明可以映射到证据，不证明证据在语义上支持答案。
- Source命中只代表找到了正确文件；Evidence命中要求完整覆盖标注引文。多事实题可能只命中一部分证据，必须再检查 `sufficient_evidence@k`。
- JSONL日志记录发生过什么；模型/工具调用次数、时间和上下文预算限制循环。历史日志不是长期记忆或恢复检查点。
- 未返回的Token用量保留未知；测试替身与真实模型质量评测是不同证据。
