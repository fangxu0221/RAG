# 架构与数据流说明

RailPolicy RAG 通过 Streamlit 和命令行提供铁路政策问答。两种入口共用检索装配逻辑。固定 RAG 先检索再生成，原生 Agent 与 LangGraph Agent 通过同一组工具检索和补读原文。各模块的依赖关系和入口见 [代码分层与阅读导航](代码分层与阅读导航.md)。

## 1. 普通终端问答的数据流

```text
cli.main → run_answer
  → bootstrap.build_retriever：读配置、验冻结清单、加载文档、切块、构造检索器
  → retriever.search(question, top_k)
      BM25 + BGE → RRF候选 → Cross-Encoder → 最终Top-K
  → generator.generate(question, results)
      编号证据 → system/user提示词 → 模型请求
  → GenerationResult：回答、Token用量和耗时
  → 终端打印
```

原生 Agent 从 `agent.main` 进入。入口创建 `DeepSeekToolModel`，通过 `KnowledgeTools.from_config()` 取得 bootstrap 装配的检索器和文档快照，再注入 `workflows.native_agent.run_agent()`。模型先提出工具调用，`ToolSession` 校验并执行 `search_knowledge` 或 `read_document`，将结果按 `tool_call_id` 送回。搜索使用配置指定的检索链，补读按来源 ID 和规范化字符窗口读取。JSONL 写入委托给存储适配器。

图版从 `langgraph_cli.main` 进入，使用同一套装配逻辑。工作流由 StateGraph 的条件边推进。模型输出和工具观察仍用原始字典消息传递，结果和 Trace 与原生 Agent 共用封装逻辑。

普通问答生成答案后结束。Judge只在答案评测入口运行。

## 6. LangGraph Agent V1

Python 入口为 `run_langgraph_agent(question, tools, model, trace_dir, limits)`。传入的 `KnowledgeTools` 持有检索器与文档快照。每次调用打开一个 `ToolSession`，模型、会话、预算和计时起点由节点闭包持有。收尾节点把业务终态写入同一份 JSONL，退出会话时记录 `request_finished` 并关闭 Trace。图在进程内运行，本地 Trace 用于复盘。

| 节点或路由 | 与原生循环的对应逻辑 |
| --- | --- |
| `model_node` | 检查模型次数、剩余时间和消息字符数，计算 `allow_tools`，调用共用的 `_call_model`。它保留 `_usage`、`_message`、模型事件和错误脱敏。返回后再检查时间、工具批量额度、结束原因及调用 ID。 |
| `_route_after_model` | 读取终态和待处理消息。已有终态进入收尾，有工具调用进入工具节点，其余进入答案校验。 |
| `tools_node` | 按顺序检查时间并计入尝试预算。共用的 `_tool_message` 规范化和去重参数，经 `ToolSession.call` 执行工具，将稳定引用编号和匹配原调用 ID 的观察结果写回。 |
| `_route_after_tools` | 时间耗尽时收尾，否则回到模型节点。模型次数已用尽时，模型节点直接返回 `model_budget`。 |
| `validate_answer_node` | 通过 `_answer_outcome` 检查结束原因、空答案、引用边界、证据和拒答前缀。 |
| `finalize_node` | 共用 `_finish` 生成结果，包括证据、引用、停止原因、计数和 Token 用量，并记录 `agent_finished`。 |

`AgentState` 中只有 `messages` 使用 `operator.add`，每个工具节点追加本轮 assistant 消息和有序 tool 消息。其他键按节点返回值覆盖。`question` 保存请求原文，`pending_message` 和 `finish_reason` 保存当前响应，`evidence` 和 `evidence_keys` 保存证据及编号映射，`calls_seen` 和 `ids_seen` 负责区分参数重复和 ID 重用。`model_calls`、`tool_attempts`、`known_token_usage` 和 `usage_complete` 记录累计统计。`status`、`stop_reason`、`answer`、`citations` 与 `result` 用于输出终态。工具节点先复制会更新的状态容器，再返回新值。

超出剩余额度的整个工具批次在执行前被拒绝。无效 JSON 或重复参数也计入尝试次数，只有经过会话分发的调用才计入 Trace 中的 `tool_calls`。模型缺报用量时，`token_usage` 为 `null`，已知的用量继续累计在 `known_token_usage`。两种编排的时限均在模型调用前后及每次工具执行前检查，图的构建与调度开销也计入实际运行时间。

本次在 Python 3.12、LangGraph 1.2.20 运行 116 项离线回归，包括 94 项原有测试和 22 项图版专项测试。专项使用相同的 ScriptedModel 脚本和本地 BM25 比较业务结果、模型请求和 JSONL 事件，计时用可控时钟，另记录实际节点执行顺序。模型质量、BGE 和重排推理沿用各自独立验证流程。[安装及复验命令](本地运行指南.md#langgraph-agent-v1)

## 7. RailPolicy RAG Studio V1

[界面入口](../ui/app.py)把当前策略、Top-K、覆盖参数和问答草稿保存在 Streamlit 会话中。`ui/runtime.py` 从选中的铁路配置加载文档快照并合并会话覆盖项。知识库目录只展示快照里的文档，使用 `sources.json` 组织标题和分类，使用 `units.jsonl` 定位原文条目。检索器仍通过 `build_retriever_from_documents()` 切块并装配。索引缓存依赖文档内容与影响构建的参数，单独修改 Top-K 时可继续复用已有检索器。

纯 RAG 把排序结果交给 `DeepSeekGenerator.generate()`，引用编号对应这次检索的顺序。两个 Agent 将同一个检索器和文档快照注入 `KnowledgeTools`，分别走原生循环和 LangGraph 图，引用编号来自工具实际取得的证据。Agent 的工具 Top-K 由调用参数决定，省略时为 3。轨迹保留每次工具请求的参数和返回数量，便于区分请求参数、实际命中数和跨调用引用编号。

本版共通过 126 项单元与应用测试，包含 10 项 Studio 测试。问答用测试替身验证，四种策略在铁路语料上执行了真实检索冒烟测试。[本地安装、启动和验证](本地运行指南.md#railpolicy-rag-studio-v1)

Studio 默认从 `ui/runtime.py` 注入同一段「通俗简洁」提示。`DeepSeekGenerator` 和两个 Agent 入口用可选 `answer_style` 参数把它附加到原系统提示词。原生和 LangGraph 共用 Agent 消息装配及 Trace 记录逻辑，模型请求和 `agent_started` 记录使用同一份系统提示。样式提示计入原有上下文预算。CLI 省略该参数，继续使用冻结评测所依赖的默认提示词。

样式更新后通过 128 项测试和 V2-auto 四组历史排名重放。两道代表性问题用真实 BM25 检索和离线模型回复核对提示注入、工具循环与证据引用，真实模型生成质量待实测。

Studio 的稠密索引缓存以 Chunk 内容和 BGE 配置为键。BGE、RRF 和重排共用同一个稠密检索器，切换策略只准备各自新增的部分。构建索引时优先尝试本机已有的 BGE 快照，快照缺失或无法完整加载时走原模型加载流程。运行统计用独立计时区分索引准备、检索和模型调用。基准 CLI 按原装配方式运行。
